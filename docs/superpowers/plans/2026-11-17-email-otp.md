# Email OTP Verification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** During registration, prove control of the entered email with a 6-digit code sent from a dedicated Gmail account through a Supabase Edge Function, and record an unforgeable `email_verified` flag on the profile.

**Architecture:** A new `email-otp` Edge Function sends/verifies codes over Gmail SMTP (465, implicit TLS), reading/writing two RLS-protected tables via the service-role key. A Postgres trigger derives `users_profile.email_verified` from a protected `verified_emails` table. The registration wizard gains an OTP step in step 0, gating progression on a successful verify.

**Tech Stack:** Deno Edge Functions (`npm:nodemailer`), Supabase PostgREST + service role, Flutter/Dart, `supabase_flutter`.

**Spec:** `docs/superpowers/specs/2026-11-17-notification-deeplink-and-email-otp-design.md` (Part 2)

## Global Constraints

- `flutter analyze` zero errors; `flutter test` green. Verify order: `flutter analyze` → `flutter test`.
- `npx --yes deno@latest check supabase/functions/email-otp/index.ts` must exit 0.
- No new Flutter dependencies. `npm:nodemailer` is Edge-Function-side only.
- No Supabase Auth. RLS stays `USING (true)` for existing tables; the two new OTP tables get RLS enabled and **no** anon/authenticated policies (service role only).
- Secrets: `GMAIL_EMAIL`, `GMAIL_APP_PASSWORD`, `OTP_PEPPER`, `SUPABASE_SERVICE_ROLE_KEY` — in Supabase secrets only, never `.env` or client code. Deploy with plain `supabase functions deploy email-otp` (config pins `verify_jwt: false`; do NOT pass `--no-verify-jwt`).
- SMTP on port 465 with `secure: true` (Supabase blocks 25/587).
- Response never echoes the code; generic errors to avoid account enumeration.
- New UI copy in all three ARB files + `flutter gen-l10n`; no hardcoded strings.
- `setup.sql` mirrors the migration for fresh projects.

## Review Focus

- **OTP for an email whose profile does not exist yet** → `verified_emails` row must precede the profile insert; pinned by the ordering check in Task 4 and the trigger semantics in Task 1.
- **Client forges `email_verified` by writing it in its own insert/update** → trigger overwrites the value from `verified_emails`; pinned in Task 1 trigger + Task 4 assertion that signUp omits the column.
- **Anon client reads or writes the OTP tables** → RLS enabled with no client policies; pinned by inspecting the migration in Task 1.
- **Wrong/expired/too-many-attempts code** → 400 with no hint, attempts capped at 5, 5-minute expiry; pinned in Task 2.
- **Missing secrets / function not deployed** → registration shows an explicit error and does not advance; pinned in Task 4 test where `verifyCode` returns a failure result.
- **Resend spam** → 60s cooldown + max 3 sends/hour per email; pinned in Task 2.

### Task 1: OTP schema migration + setup.sql mirror

**Files:**
- Create: `supabase/migrations/20261117_email_otp.sql`
- Modify: `setup.sql` (after `users_profile` DDL ~174-229)

**Interfaces:**
- Produces tables `public.email_otps` (email PK, code_hash, expires_at, attempts, last_sent_at, created_at) and `public.verified_emails` (email PK, verified_at); column `public.users_profile.email_verified BOOLEAN NOT NULL DEFAULT FALSE`; trigger function `public.set_email_verified()`.

- [ ] **Step 1: Write the migration**

```sql
-- Email OTP verification. Client roles have NO access; service role only.
CREATE TABLE IF NOT EXISTS public.email_otps (
  email        TEXT PRIMARY KEY,
  code_hash    TEXT NOT NULL,
  expires_at   TIMESTAMPTZ NOT NULL,
  attempts     INT NOT NULL DEFAULT 0,
  last_sent_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
ALTER TABLE public.email_otps ENABLE ROW LEVEL SECURITY;

CREATE TABLE IF NOT EXISTS public.verified_emails (
  email       TEXT PRIMARY KEY,
  verified_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
ALTER TABLE public.verified_emails ENABLE ROW LEVEL SECURITY;

ALTER TABLE public.users_profile
  ADD COLUMN IF NOT EXISTS email_verified BOOLEAN NOT NULL DEFAULT FALSE;

CREATE OR REPLACE FUNCTION public.set_email_verified()
RETURNS TRIGGER LANGUAGE plpgsql SECURITY DEFINER SET search_path = public AS $$
BEGIN
  NEW.email_verified := EXISTS (
    SELECT 1 FROM public.verified_emails v WHERE v.email = NEW.email
  );
  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS trg_set_email_verified ON public.users_profile;
CREATE TRIGGER trg_set_email_verified
  BEFORE INSERT OR UPDATE OF email, email_verified ON public.users_profile
  FOR EACH ROW EXECUTE FUNCTION public.set_email_verified();
```

Note: no `CREATE POLICY` for anon/authenticated on the two new tables — that is intentional and is the security boundary.

### Task 2: `email-otp` Edge Function

**Files:**
- Create: `supabase/functions/email-otp/config.json`
- Create: `supabase/functions/email-otp/index.ts`

**Interfaces:**
- Consumes: secrets `GMAIL_EMAIL`, `GMAIL_APP_PASSWORD`, `OTP_PEPPER`, `SUPABASE_SERVICE_ROLE_KEY`; shared helpers in `supabase/functions/ai/_shared.ts`.
- Produces: `POST /` with body `{ action: 'send'|'verify', email: string, code?: string }` → JSON `{ ok: true }` or `errorResponse(status, code, message)` (shared helper signature confirmed in `_shared.ts:43`).

- [ ] **Step 1: Write config and function**

`config.json` = `{ "verify_jwt": false }`.

`index.ts`: static imports only (deploy bundler requirement) — `serve` from deno std, `corsHeaders`/`jsonResponse`/`errorResponse` from `../ai/_shared.ts`, `nodemailer` from `npm:nodemailer`. Handle `OPTIONS`. Read all four secrets at startup; if any missing return 500 `config_error`. Follow `push/index.ts`'s raw-fetch pattern for DB access: `restGet`/`restPost`/`restDelete` helpers against `${SUPABASE_URL}/rest/v1/<table>` with headers `apikey: SERVICE_ROLE_KEY`, `Authorization: Bearer ${SUPABASE_SERVICE_ROLE_KEY}`, `Content-Type: application/json`, and `Prefer: return=representation` on writes. Do not add a Supabase client library — raw fetch is the established convention here.

`send`: validate email with a simple regex; enforce cooldown (`now - last_sent_at < 60s` → 429) and max 3 sends/hour (count via created_at or a counter column — choose the simplest correct approach); generate 6 digits from `crypto.getRandomValues`; store SHA-256 of `OTP_PEPPER + code` (Web Crypto `crypto.subtle.digest`) with `expires_at = now + 5min`, reset attempts to 0; send via nodemailer `createTransport({host:'smtp.gmail.com', port:465, secure:true, auth:{user:GMAIL_EMAIL, pass:GMAIL_APP_PASSWORD}})` with plain + HTML text. Return `{ok:true}` — never the code.

`verify`: load row by email; if none/expired → 400 generic `invalid_code`; if `attempts >= 5` → 429; compare hash (constant-time compare not required for 6 digits with a pepper, but do a full string compare); on match insert into `verified_emails` (upsert on conflict), delete the `email_otps` row, return `{ok:true}`; on mismatch increment `attempts` and return 400 `invalid_code`.
